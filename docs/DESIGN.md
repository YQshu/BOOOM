# Design 文档（Off-Grid / 离线）

> 目标：用于规划三周内参赛版本需要完成的功能、内容与验收标准，保证双人协同开发节奏一致。

## 1. 项目目标

- 在 GJam 截止前交付一个可完整游玩的参赛版本。
- 完成核心玩法闭环：
  - 多角色记忆周目切换
  - 不可靠叙事
  - 跨周目线索比对
  - 盲区解锁
  - 分支结局

## 2. 本期范围（In Scope）

### 2.1 核心系统

1. 玩家移动与基础交互（俯视角）
2. 线索收集与线索列表 UI
3. 周目切换（2~3 个角色视角）
4. 盲区解锁（由线索触发）
5. 旁白触发与冲突叙事
6. 凶手指认与结局判定

### 2.2 内容规模（建议）

- 场景：1 个主场景（通过状态变化表达不同周目）
- 角色：2~3 个可切换视角角色
- 关键线索：6~10 条
- 结局：至少 2 个（坏结局 + 真结局）

## 3. 非范围（Out of Scope）

- 战斗系统
- 大地图与多关卡扩展
- 复杂数值成长系统
- 商业化相关功能（内购、账号系统等）

## 4. 系统设计概览

### 4.1 核心循环

1. 选择角色进入周目
2. 探索并交互收集线索
3. 触发旁白与冲突信息
4. 切换其他角色周目进行交叉验证
5. 解锁盲区并补全事实链
6. 指认凶手进入结局

### 4.2 系统模块

- `LoopManager`：周目加载、切换、状态管理
- `ClueManager`：线索注册、收集、查询
- `NarrationManager`：旁白触发与管理
- `MemoryLockZone`：黑屏/禁区解锁逻辑
- `EndingManager`：指认与结局判定

## 5. 三周里程碑

## Week 1（MVP 闭环）

- 完成玩家控制、交互、线索拾取
- 完成 1 个周目完整流程（进入→探索→退出）
- 基础 UI：交互提示、线索列表

验收标准：

- 可从开始进入一个可玩流程并完成一次线索收集闭环

## Week 2（核心玩法实现）

- 接入 2~3 角色周目切换
- 完成盲区解锁机制
- 完成跨周目线索联动
- 接入旁白触发与冲突叙事

验收标准：

- 玩家可通过切换角色补全单角色无法获得的信息

## Week 3（结局与打磨）

- 完成指认流程和结局分支
- 完成真结局触发条件
- 优化引导、音效、节奏
- Bug 修复与最终打包

验收标准：

- 全流程可跑通，至少一个坏结局和一个真结局可稳定触发

## 6. 任务拆分（双人协作）

### 程序 A（系统向）

- 周目切换与全局状态管理
- 盲区解锁逻辑
- 结局判定与流程状态机

### 程序 B（玩法向）

- 玩家移动与交互系统
- 线索系统与 UI
- 旁白触发系统

> 每日同步点：接口字段、事件命名、数据结构变更。

## 7. 数据与命名约定

- 线索 ID：`CLUE_<区域>_<编号>`（示例：`CLUE_ROOM_01`）
- 周目 ID：`LOOP_<角色名>`（示例：`LOOP_SUSPECT_A`）
- 结局 ID：`ENDING_<类型>`（示例：`ENDING_BAD_WRONG_ACCUSATION`）

## 8. 风险与应对

1. **风险：** 场景/Prefab 冲突频繁
   - **应对：** 分时编辑；大改前建立回滚点；尽量减少同文件同时修改

2. **风险：** 内容超量导致无法收尾
   - **应对：** 严格冻结范围；优先保证主流程可玩

3. **风险：** 周目联动逻辑复杂导致 Bug
   - **应对：** 使用统一状态源（Manager），避免多个脚本各自维护真相

## 9. 每日完成定义（DoD）

一个任务只有在满足以下条件后才算完成：

- 功能可在 Unity 内运行验证
- 不影响已有主流程
- 命名与格式符合 `docs/CODE_STYLE.md`
- 已提交到独立分支并写清提交信息
- 已在 PR 描述中写明测试步骤

## 10. 版本冻结策略

- 截止前 48 小时停止新增功能
- 仅允许修复阻断体验的 Bug
- 每次修复必须附带复现步骤与验证结果
